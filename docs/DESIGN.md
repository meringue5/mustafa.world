## UI 설계

### 기본 방향

-   웹에서 실행하되, UI는 일반 DOM 컴포넌트가 아니라 `xterm.js` 기반 TUI로 구성한다.
-   화면은 xterm.js 터미널 버퍼 위에 ANSI 출력으로 그린다.
-   로그, 상태 표시, 입력 후보, 입력줄은 모두 터미널 내부 출력으로 취급한다.
-   DOM 버튼이나 별도 GUI 입력창으로 터미널 입력을 대체하지 않는다.

### 폰트

기본 터미널 폰트는 `IyagiGGCHalf`를 사용한다.

`IyagiGGCHalf`는 도스 시절 PC통신 에뮬레이터 이야기 5,3의 굵은체를 복각한 이야기 굵은체의 반각 버전이다. UTF-8 터미널 환경에서 도형문자 폭이 흔들리는 문제를 줄이기 위해 이 버전을 우선한다.

웹폰트 선언:

```css
@font-face {
  font-family: "IyagiGGCHalf";
  src: url("https://cdn.jsdelivr.net/gh/JuwanPark/IyagiGGC@latest/IyagiGGCHalf.woff") format("woff");
  font-weight: normal;
  font-style: normal;
}
```

참조:

-   `https://pjw48.net/iyagiggc/`
-   `https://github.com/JuwanPark/IyagiGGC`

웹폰트가 늦게 로드되면 xterm.js의 셀 폭 계산이 달라질 수 있으므로, 폰트 로딩 이후 터미널 `fit()`을 다시 수행한다.

xterm.js 설정:

-   `customGlyphs`는 `false`로 둔다. 박스 드로잉과 블록 문자를 xterm 자체 도형이 아니라 `IyagiGGCHalf` 글리프로 그리기 위해서다.
-   `lineHeight`는 `1`로 둔다. 박스 드로잉 문자의 세로 연결이 벌어지지 않게 한다.
-   `fontWeightBold`는 `normal`로 둔다. `IyagiGGCHalf`는 기본 woff만 사용하므로 브라우저의 합성 bold가 셀 폭과 글리프 밀도를 흔들지 않게 한다.
-   가능하면 `font-feature-settings: "ss01" 1`을 적용한다. xterm의 canvas 렌더러가 모든 OpenType feature를 보장하지는 않지만, DOM/CSS 경로에서 이야기 특수문자 스타일을 우선한다.

### 컬러 팔레트

터미널 UI의 색은 ANSI 16색 팔레트만 사용한다.

화면을 그리는 ANSI 출력에서는 24-bit RGB escape sequence를 사용하지 않는다. 색상은 xterm.js의 16색 슬롯과 SGR 코드만 사용한다.

기본 팔레트:

```text
black          red          green          yellow
blue           magenta      cyan           white
brightBlack    brightRed    brightGreen    brightYellow
brightBlue     brightMagenta brightCyan     brightWhite
```

용도:

-   기본 본문: `white`
-   약한 정보, 박스 선: `brightBlack`
-   장소 타이틀: `brightYellow`
-   사물 하이라이트: `cyan`
-   행위자 하이라이트: `brightMagenta`
-   링크 하이라이트: `green`
-   오류: `red`
-   HP 게이지: `red` 배경
-   MP 게이지: `blue` 배경
-   STA 게이지: `green` 배경
-   비어 있는 게이지: `brightBlack` 배경

CSS와 xterm.js theme에서는 위 16색 슬롯을 실제 화면 색으로 매핑할 수 있지만, 앱이 그리는 TUI는 이 16색 이름 밖의 색을 직접 요구하지 않는다.

### 특수문자 활용

`IyagiGGCHalf`에는 도스/PC통신 시절 TUI 감각을 낼 수 있는 특수문자와 도형문자가 포함되어 있다. UTF-8 터미널 환경에서는 반각 버전을 우선 적용한다.

활용 후보:

-   박스 드로잉: `─`, `│`, `┌`, `┐`, `└`, `┘`, `├`, `┤`, `┬`, `┴`, `┼`
-   블록/채움 문자: `■`, `□`, `▣`, `▤`, `▥`, `▦`, `▧`, `▨`, `▩`, `▒`
-   방향/선택 표시: `▶`, `▷`, `◀`, `◁`, `▲`, `▼`, `→`, `←`, `↑`, `↓`
-   단계형 게이지 문자: `▁`, `▂`, `▃`, `▅`, `▆`, `▇`

단계형 게이지 문자는 궁극기 쿨타임, 차지 상태, 스킬 준비도처럼 숫자보다 감각적인 상태 표시에 사용할 수 있다.

예시:

```text
ULT ▁▂▃▅▆▇
```

현재 `HP`, `MP`, `STA` 상태바는 ANSI 16색 배경색 기반 bar gauge를 우선 사용한다. 특수문자 게이지는 향후 스킬, 쿨타임, 모드, 임시 상태 표시 등에 적용할 후보로 둔다.

### 본문 영역: 장소 표시 방식

본문 영역은 현재 장소를 보여주는 장소 UI를 기본으로 한다.

장소 UI는 다음 순서로 렌더링한다.

1.  장소 타이틀
2.  장소 설명
3.  행위자 라인
4.  연결 라인

예시:

```text
서재

읽고 쓰고 생각을 펼치는 장소다. 책상 위에는 노트북이 열려 있고,
책장에는 아직 읽다 만 책들이 꽂혀 있다.

노아가 책상 위에 드러누워 있다.

연결: 거실, 서재 베란다
```

장소 설명은 정적인 공간 묘사다. 방의 분위기, 배경 사물, 상호작용 가능한 사물을 자연스럽게 포함할 수 있다.

현재 장소 UI는 화면 상단에 고정하지 않는다. 입력 영역을 제외한 본문 영역은 하나의 흐르는 텍스트 버퍼이며, 이동하거나 `살펴봐`를 실행할 때 그 시점의 장소 스냅샷이 본문 흐름에 추가된다.

이 구조를 택하는 이유:

-   MUD의 핵심 감각은 고정 패널보다 텍스트가 누적되는 진행감에 가깝다.
-   장소 설명도 사건의 일부로 남아야 나중에 스크롤해 맥락을 되짚을 수 있다.
-   하단 입력 영역만 고정하면 입력 집중은 유지하면서 본문은 터미널답게 흐른다.

스크롤은 부드러운 픽셀 스크롤이 아니라 라인 단위 스크롤로 처리한다. 사용자는 본문을 한 줄씩 올리고 내리며 이전 장소 스냅샷과 이벤트를 확인할 수 있다.

상호작용 가능한 사물이나 대상은 장소 설명 안에서 색을 다르게 표현할 수 있다.

행위자는 장소 설명에 녹이지 않는다. 행위자는 현재 장소에 존재하는 동적 대상이며, 장소 설명 아래에 별도 라인으로 출력한다.

행위자 라인은 현재 상태나 자세를 보여준다.

예시:

```text
노아가 책상 위에 드러누워 있다.
노아가 당신을 빤히 본다.
노아가 자기 발바닥을 핥는다.
```

연결 라인은 현재 장소에서 이동 가능한 장소 링크를 보여준다.

```text
연결: 거실, 서재 베란다
```

장소 설명과 행위자 라인은 서로 다른 성격을 가진다.

-   장소 설명: 비교적 정적이다.
-   행위자 라인: 상태, tick, 이벤트에 따라 바뀔 수 있다.
-   연결 라인: 현재 장소의 `links`를 표시한다.

모든 본문 라인에 시간을 붙이지 않는다. 시간은 이벤트 로그에서 필요할 때만 제한적으로 사용하거나, 상단/상태 영역에 별도로 둔다.

### 하단 입력 UI

화면 하단의 커맨드 입력 영역은 항상 5줄 고정 높이를 가진다.

1.  상단 박스선
2.  상태 표시줄
3.  커맨드 후보 표시줄
4.  커맨드 입력줄
5.  하단 박스선

커맨드 후보 수가 바뀌어도 하단 입력 영역의 높이는 변하지 않는다. 후보는 한 줄 안에서 압축해 보여준다.

입력 영역은 박스로 감싼다. xterm.js의 `customGlyphs`는 끄고, `IyagiGGCHalf` 폰트의 글리프가 직접 렌더링되도록 한다.

현재 5줄 구조:

```text
┌────────────────────────────────┐
│  HP ... MP ... STA ... LOC 서재 │
│  후보 표시줄                    │
│  입력                           │
└ 예비 표시 또는 하단선 ─────────┘
```

박스 내부에는 좌우 2셀 padding을 둔다. 현재는 유니코드 박스 드로잉 문자로 렌더링하되, IyagiGGCHalf의 DOS식 전용 도형문자 매핑이 확인되면 해당 문자로 교체한다.

### 상태 표시줄

상태 표시줄에는 `HP`, `MP`, `STA`를 표시한다.

-   `HP`: 빨강 계열 bar gauge
-   `MP`: 파랑 계열 bar gauge
-   `STA`: 초록 계열 bar gauge

각 스탯은 `80/100` 같은 숫자 값을 함께 표시한다. 숫자는 게이지 위에 올라가며, 게이지의 채워진 배경이 현재 값을 나타낸다.

예시:

```text
HP [      80/100  ]  MP [      50/100      ]  STA [      70/100     ]  LOC living
```

실제 렌더링에서는 `[]` 문자 자체를 쓰는 것이 아니라, xterm ANSI 16색 배경색으로 게이지 영역을 칠한다.

### 커맨드 후보 표시줄

커맨드 후보는 상태 표시줄 아래 한 줄에 표시한다. 이 줄은 단순 문자열 자동완성이 아니라, 현재 입력에서 비어 있는 의미 슬롯을 채우기 위한 후보를 보여준다.

입력줄이 비어 있을 때 후보 표시줄은 아무것도 보여주지 않는다. 사용자가 무언가를 입력하기 전에는 시스템이 먼저 가능한 행동 목록을 펼치지 않는다.

후보는 사용자가 단어를 확정했다는 신호가 있을 때만 생성한다. 현재 기준은 입력이 공백으로 끝나는 것이다.

후보 생성 우선순위:

1.  동사 기반 추천
2.  명사/대상 기반 추천

동사 기반 추천은 사용자가 동사나 동사 어간을 입력했을 때 먼저 작동한다.

예시:

```text
먹어 
무엇을?
```

```text
가 
어디로? 거실  서재 베란다
```

명사/대상 기반 추천은 동사 기반으로 해석되지 않는 입력에 대해 작동한다.

예시:

```text
노아 
노아? 노아를  노아에게  노아와
```

하단 5줄 박스 구조는 현재 정의를 유지한다. 별도의 `문맥줄`이나 `슬롯줄`을 하단에 추가하지 않는다. 파서가 슬롯 상태를 시각화해야 할 경우, 후보줄 안의 짧은 질문 또는 하단 박스선의 짧은 표시를 사용한다.

후보줄이 보여줄 수 있는 후보 종류:

-   대상 후보: `과자`, `노아`, `책상`
-   조사 후보: `노아를`, `노아에게`, `노아와`
-   동사 후보: `먹어`, `줘`, `쓰다듬어`, `살펴봐`
-   실행/취소 후보: `실행`, `취소`, `정말 공격`

후보는 현재 비어 있는 슬롯의 질문과 함께 표시한다.

예시:

```text
무엇을? 과자  사과  물
노아? 노아를  노아에게  노아와
다음 행동 쓰다듬어  불러  살펴봐
```

후보 생성의 우선순위는 세계 상태를 따른다.

-   현재 장소에서 보이는 사물과 행위자
-   플레이어가 가진 물건
-   최근 로그나 장소 설명에서 언급된 대상
-   현재 장소와 연결된 장소
-   현재 상황에서 이미 발견했거나 배운 상호작용
-   전체 단어장

숨겨진 퍼즐 해법이나 아직 발견하지 못한 상호작용은 후보줄에 노출하지 않는다. 후보줄은 힌트 시스템이 아니라, 플레이어가 이미 볼 수 있거나 알 수 있는 행동을 조립하게 돕는 장치다.

조작 원칙:

-   현재 선택된 후보는 괄호 문자를 추가하지 않고 ANSI 반전색으로 표시한다.
-   후보 선택은 `←`, `→` 키로 이동한다.
-   `Tab`은 선택된 후보를 입력줄에 채운다.
-   `Enter`는 완성된 명령을 실행하거나 현재 후보를 확정한다.
-   후보줄의 후보를 마우스로 클릭하면 현재 후보를 확정한다. 이는 DOM 버튼이 아니라, xterm 화면의 터미널 행/열을 셀 좌표로 환산해 후보를 고르는 보조 입력이다.
-   후보 표시줄은 높이를 늘리지 않는다.
-   후보는 한 줄에 읽히는 수준으로 제한한다. 너무 많아지면 검색 UI가 되므로 보통 4~7개 안에 둔다.

예시:

```text
어디로? 거실  서재 베란다
```

`가 `처럼 동사를 먼저 입력하고 공백으로 단어를 확정한 상태에서 장소 후보를 확정하면, 후보는 동사 뒤에 붙는 것이 아니라 비어 있던 목적지 슬롯에 들어간다.

```text
가 
어디로? 거실  서재 베란다
```

여기서 `거실`을 확정하면 입력줄은 다음처럼 바뀐다.

```text
거실로 가
```

### 커맨드 입력줄

입력줄에는 별도의 프롬프트 문자 `>`를 표시하지 않는다. 하단 박스의 입력줄 자체와 커서가 입력 위치를 나타낸다.

```text
go workroom
```

기본 조작은 타이핑이다. 입력 보조는 존재하지만, GUI 버튼으로 대체하지 않는다.

### 한글 입력 경계

xterm.js의 `onData`가 넘긴 확정 입력만 명령 버퍼로 취급한다. 한글 IME 조합 중인 글자를 xterm 내부 helper textarea에서 미리 읽거나, 완성 전 토큰을 추정하지 않는다.

후보 추천은 확정 입력이 공백으로 끝나는 단어 경계에서만 열린다.

-   `가`: 후보 없음
-   `가 `: `어디로?`와 장소 후보 표시
-   `노아`: 후보 없음
-   `노아 `: 현재 세계 상태에 맞는 대상 기반 후보 표시

이 규칙은 macOS 한글 IME처럼 조합 중인 글자가 화면에는 보이지만 앱 입력 버퍼에는 확정되지 않은 상태를 피하기 위한 것이다. 사용자가 공백을 입력하면 그 단어가 완성되었다고 보고, 그때부터 추천을 계산한다.

### 예비 표시

하단 박스선은 필요할 때 짧은 예비 표시를 담을 수 있다.

현재 용도:

-   향후 모드 표시
-   임시 메시지
-   입력 보조의 2차 정보
-   입력 모드나 임시 상태 표시

초기 프로토타입에서는 대부분 비워두고, 본문을 위로 스크롤했을 때 `SCROLL +N` 같은 짧은 상태만 표시한다.

## 월드/맵 설계

### 기본 방향

월드는 장소와 장소의 연결로 구성한다.

내부 표상은 그래프 자료구조를 기본으로 한다.

-   장소는 노드다.
-   장소 간 연결은 엣지다.
-   플레이어의 현재 위치는 현재 노드다.
-   이동은 현재 노드에서 연결된 다른 노드로 상태를 바꾸는 것이다.

### 방향 이동 비채택

전통적인 MUD는 동서남북, 위아래 같은 방향 이동으로 거리감과 공간감을 표현한다.

이 프로젝트에서는 방향 기반 이동을 기본 모델로 채택하지 않는다.

이 프로젝트는 물리적 지형을 세밀하게 시뮬레이션하는 게임이 아니라, 개인의 월드 모델을 구축하는 프로젝트다. 따라서 중요한 것은 실제 거리나 방향이 아니라, 사용자가 기억하고 경험하는 장소 간 연결이다.

예를 들어 집과 회사가 실제로 30km 떨어져 있더라도, 사용자의 경험은 도로 위의 모든 중간 지점을 직접 이동하는 것이 아닐 수 있다.

```text
집 -> 셔틀 -> 회사
```

이 경우 `셔틀`은 동서남북 이동의 연속이 아니라 장소와 장소를 연결하는 포탈에 가깝다. 사용자는 셔틀에 타고, 눈을 감았다 뜨면 회사에 도착한다. 이 경험을 표현하기 위해 중간 경로를 `북 북 북 서 서 서 ...` 같은 방향 이동으로 쪼갤 필요는 없다.

### 장소 링크

장소는 방향이 아니라 의미 있는 링크로 연결한다.

예시:

```text
집 -> 회사
집 -> 동네 카페
회사 -> 퇴근길 셔틀 정류장
거실 -> 작업실
작업실 -> 프로젝트 저장소
```

링크는 물리적 인접성뿐 아니라 습관, 이동 수단, 기억, 업무 흐름, 디지털 공간 연결도 표현할 수 있다.

예시 링크 유형:

-   문
-   복도
-   셔틀
-   엘리베이터
-   즐겨찾기
-   터미널 명령
-   루틴
-   기억
-   업무 흐름

### 엣지 메타데이터

엣지는 단순 방향보다 풍부한 이동 경험을 담을 수 있다.

후보 속성:

```yaml
links:
  - to: company.office
    label: 회사
    type: shuttle
    aliases: [회사, 셔틀, 출근]
    description: 집 앞 정류장에서 셔틀을 타고 회사로 간다.
```

초기에는 `to`, `label`, `type`, `aliases` 정도만 고려한다. `label`은 이동 행위 문장이 아니라 링크가 가리키는 장소명 또는 짧은 목적지명으로 둔다. `나간다`, `들어간다`, `간다` 같은 동사는 링크 라벨에 넣지 않는다.

향후 필요하면 다음 속성을 추가할 수 있다.

-   조건
-   잠금 여부
-   비용
-   소요 시간
-   사용 가능한 시간대
-   감정적 거리
-   최근 사용 빈도

### Obsidian 기반 맵 제작

맵 제작은 Obsidian Vault를 우선 검토한다.

각 장소는 Markdown 파일 하나로 표현하고, 장소 간 연결은 frontmatter의 `links` 또는 이에 준하는 구조화 필드로 표현한다.

Obsidian의 문서 링크와 Graph View는 시각적 검토에 사용할 수 있지만, 게임의 source of truth는 구조화된 링크 메타데이터로 둔다.

Canvas 파일은 필요하면 장소의 시각적 배치나 개발용 지도 검토에 사용한다. 초기 필수 요소는 아니다.

초기 제작용 vault는 `world-vault/`에 둔다.

Vault 내부에서 `_templates/`는 Obsidian Templates 플러그인으로 삽입하는 실제 템플릿만 둔다. 패턴 사전, 작성 규칙, 예시는 `_references/`에 둔다.

현재 홈 예시 노드:

-   현관
-   거실
-   침실
-   주방
-   작은방
-   서재
-   주방 베란다
-   서재 베란다
-   거실 베란다

홈 예시에서는 `거실`을 허브 노드로 두고, 각 베란다는 붙어 있는 방에서 접근하는 장소 링크로 둔다. 실제 집의 감각 구조와 다르면 Markdown 파일의 `links`를 수정한다.

### 앱 데이터 흐름

장소 데이터의 source of truth는 `world-vault/rooms/**/*.md`다.

온톨로지 데이터도 우선 `world-vault/` 안에서 작성한다. 별도 전문 온톨로지 툴을 바로 도입하지 않고, `Obsidian-first, export-later` 방침을 따른다. 자세한 내용은 [`docs/design/ontology.md`](design/ontology.md)에 둔다.

앱 런타임은 Markdown 파일을 직접 해석하지 않고, 컴파일된 JSON 그래프를 사용한다.

```text
world-vault/rooms/**/*.md
  -> scripts/build-world.mjs
  -> src/generated/world.json
  -> src/world.js
```

`npm run build:world`는 vault의 장소 Markdown을 읽어 `src/generated/world.json`을 생성한다.

`npm run dev`와 `npm run build`는 실행 전에 `build:world`를 수행한다.

현재 시작 위치는 `home.study`다.

설계 문서와 레퍼런스 문서는 규칙과 의도를 설명한다. 실제 앱에서 돌아다니는 장소와 링크는 vault의 장소 Markdown과 생성된 JSON을 기준으로 한다.

### 스키마 변경과 리팩터링

초기 vault의 장소 파일과 템플릿은 고정된 최종 형식이 아니다.

월드 모델이 자라면 다음 변화가 생길 수 있다.

-   템플릿 필드 추가/삭제
-   `links` 구조 변경
-   링크 타입 명칭 변경
-   조건 표현 방식 변경
-   장소 id 규칙 변경
-   기존 장소 파일의 frontmatter 정규화

따라서 템플릿 변경 이후 기존 장소 파일을 맞춰 바꾸는 리팩터링 과정을 전제로 한다.

가능하면 리팩터링은 수동 편집만이 아니라 검사/마이그레이션 스크립트로 보조한다.

리팩터링 시 확인할 항목:

-   모든 장소 id가 고유한가
-   모든 `links.to`가 존재하는 장소를 가리키는가
-   양방향 링크의 상대 링크가 누락되지 않았는가
-   alias가 충돌하지 않는가
-   템플릿의 필수 필드가 기존 장소에 모두 존재하는가

### 구현 여부

이 항목은 월드 모델의 방향을 기록한 것이다.

구체적인 파일 형식, 컴파일 과정, Obsidian Vault 구조, 런타임 그래프 자료구조는 별도 검토 후 결정한다.

## 파서 설계

### 기본 방향

명령 입력은 완전한 자유 자연어 이해가 아니라, 제한된 단어장과 한국어 조사를 이용한 TUI용 명령 구성으로 접근한다.

핵심 관점:

-   동사는 함수처럼 취급한다.
-   명사는 함수에 들어가는 인자처럼 취급한다.
-   조사는 인자의 역할을 표시하는 타입 표식처럼 취급한다.

예시:

```text
사과를 철수에게 줘
```

파서 관점:

```text
verb: 주다
args:
  object: 사과
  dative: 철수
```

### 조사와 인자 역할

한국어는 SOV 어순을 가지며, 조사가 있으면 인자의 역할을 비교적 쉽게 파악할 수 있다.

예시:

```text
사과를      -> 목적격 인자
철수에게    -> 여격 인자
책상에      -> 도착지 / 위치 인자
책상에서    -> 행위 장소 인자
칼로        -> 도구 인자
```

초기 설계에서는 조사, 명사, 동사의 종류를 예약어 또는 제한된 단어장으로 둔다. 이 제한은 파서를 작고 예측 가능하게 만들고, 추천 UI가 세계가 허용하는 행동만 제안하도록 돕는다.

### 동사 시그니처

동사는 함수 시그니처를 가진다.

예시:

```text
보다(object)
가다(destination)
주다(object, dative)
놓다(object, location)
사용하다(object | tool)
```

초기 동사 목록:

```text
가(destination)
살펴보다(object?)
먹다(object)
쓰다듬다(target)
주다(object, recipient)
기다리다()
```

`가`는 기본 이동 동사다. 장소 링크의 라벨은 `거실`, `서재 베란다`처럼 장소만 보여주고, 실제 행동은 `거실로 가`, `서재 베란다로 가`, `가 거실`처럼 `가` 동사로 표현한다. `나간다`, `들어간다`는 초기 동사 목록에 넣지 않는다.

동사마다 필요한 인자와 선택 인자를 정의할 수 있다.

-   타동사인지
-   목적어가 필요한지
-   여격 인자가 필요한지
-   위치 인자가 필요한지
-   도구 인자를 받을 수 있는지

이 정보는 파싱뿐 아니라 추천에도 사용한다.

### 추천 UI와 파서의 관계

추천 UI는 단순한 문자열 자동완성이 아니라, 현재까지 채워진 인자와 비어 있는 인자 슬롯을 바탕으로 동작한다. 설계 이름은 `격 슬롯 기반 커맨드 컴포저`로 둔다.

명령 입력은 완성된 문장만 처리하지 않는다. 매 키 입력 또는 토큰 단위로 부분 입력 상태를 만들고, 그 상태에서 다음에 채워야 할 슬롯을 계산한다.

기본 슬롯:

-   `subject`: 기본값은 플레이어 자신이다.
-   `verb`: 실행할 행동이다.
-   `object`: 목적격 대상이다.
-   `recipient`: 여격 대상, 받는 이다.
-   `destination`: 이동 목적지다.
-   `location`: 위치 또는 행위 장소다.
-   `instrument`: 도구다.
-   `companion`: 함께하는 대상이다.

후보줄은 이 슬롯 중 아직 비어 있거나 애매한 슬롯을 채우는 UI다.

예시:

```text
사과를
```

파서는 `object=사과`를 확보한다. 이후 후보는 목적어를 받을 수 있는 동사를 우선 추천할 수 있다.

```text
먹어
봐
줘
놓아
```

예시:

```text
사과를 철수에게
```

파서는 `object=사과`, `dative=철수`를 확보한다. 이후 `주다` 계열 동사를 강하게 추천할 수 있다.

반대로 동사를 먼저 입력한 경우:

```text
줘
```

`주다(object, dative)` 시그니처를 보고 IDE의 파라미터 힌트처럼 필요한 인자를 추천할 수 있다.

### 동사 먼저 입력

동사를 함수처럼 보므로, 동사가 먼저 들어오면 해당 동사의 시그니처가 활성화된다.

예시:

```text
먹어
```

파서 상태:

```text
subject: 나
verb: 먹다
object: ?
```

후보줄:

```text
무엇을? 과자  사과  물
```

`먹다`가 목적어를 요구하고, 그 목적어가 `edible` 태그를 가져야 한다면 후보는 현재 장소, 인벤토리, 최근 맥락 안의 먹을 수 있는 대상에서 우선 생성한다.

예시:

```text
줘
```

파서 상태:

```text
subject: 나
verb: 주다
object/theme: ?
recipient: ?
```

후보줄은 먼저 줄 물건을 묻거나, 현재 맥락상 받는 이가 더 명확하면 받는 이를 먼저 묻는다.

`주다(object, recipient)`처럼 필수 인자가 둘 이상인 동사는 후보줄에서 비어 있는 슬롯을 함께 드러낼 수 있어야 한다.

예시:

```text
줘
무엇을? 츄르  과자    누구에게? 노아
```

이때 후보 확정은 선택된 슬롯 하나를 채운다. `츄르`를 고르면 `object=츄르`가 먼저 채워지고, 다음 후보 상태는 `누구에게? 노아`처럼 남은 슬롯을 우선한다. 반대로 `노아`를 먼저 고르면 `recipient=노아`가 채워지고, 다음 후보 상태는 `무엇을? 츄르  과자`가 된다.

```text
무엇을? 츄르  과자  장난감
누구에게? 노아에게  ...
```

### 명사/토큰 먼저 입력

명사나 행위자가 먼저 들어오면, 추천 UI는 단순히 다음 조사나 다음 단어를 예측하지 않는다.

초기 아이디어는 `노아` 입력 후 `노아를`, `노아에게`, `노아와` 같은 조사 후보를 먼저 보여주는 방식이었다. 이 방식은 한국어 파싱에는 편하지만, 사용자가 의미 있는 행동을 고르기 전에 다음 토큰을 맞히는 UI처럼 느껴진다.

따라서 명사 먼저 입력의 기본 방침은 조사 선택이 아니라 월드 상태 기반 affordance 추천이다.

예시:

```text
노아
```

권장 후보줄:

```text
쓰다듬어  불러  살펴봐  츄르를 줘
```

필요하면 격 역할별로 묶어 보여줄 수 있다.

```text
노아를: 쓰다듬어  살펴봐
노아에게: 츄르를 줘
노아와: 놀아
```

조사는 여전히 파서 내부에서 중요한 타입 표식이다. 사용자가 직접 `노아에게`, `노아를`처럼 입력하면 파서는 이를 해석한다. 하지만 기본 추천 UI는 조사 자체보다 현재 세계가 허용하는 행동을 우선 보여준다.

이 방침은 커맨드 컴포저가 일반적인 다음단어 예측기가 되지 않게 하기 위한 것이다. 후보는 언어 확률이 아니라 다음 데이터에서 나온다.

-   현재 장소의 행위자와 사물
-   플레이어의 인벤토리
-   태그: `touchable`, `edible`, `portable`, `giftable` 등
-   관계: `노아 likes 츄르`, `player has 츄르` 등
-   현재까지 발견했거나 볼 수 있는 상호작용

자세한 방침은 [`docs/design/command-composer.md`](design/command-composer.md)에 둔다.

### 조사 없는 입력

조사가 없는 입력도 허용한다.

예시:

```text
과자 먹어
노아 쓰다듬어
주방 가
```

이 경우에는 동사 시그니처와 엔티티 태그를 사용해 슬롯을 추론한다.

-   `과자`: `edible`, `portable`
-   `먹다`: `object` 필요
-   결과: `object=과자`, `verb=먹다`

추론이 애매하면 즉시 실행하지 않고 후보줄에서 명확히 한다.

예시:

```text
물
```

가능한 해석이 여러 개라면:

```text
다음 행동 마셔  집어  살펴봐
```

### 실행과 확인

필수 슬롯이 모두 채워지면 후보줄은 실행 후보를 보여줄 수 있다.

```text
실행
```

위험하거나 감정적으로 중요한 행동은 즉시 실행하지 않고 확인 후보를 띄운다.

```text
노아 공격
취소  정말 공격  쓰다듬어
```

이 확인은 실수 방지와 세계의 감정적 무게를 표현하기 위한 장치다.

### 지역과 맥락 기반 단어 추천

파라미터가 될 단어 추천은 사용자가 머무르는 지역과 현재 맥락을 우선한다.

MUD적 공간 구조에서는 현재 방, 인접 방, 인벤토리, 최근 상호작용 대상이 추천 후보의 우선순위에 영향을 줄 수 있다.

초기 우선순위 예시:

1.  현재 방에 존재하는 명사
2.  현재 방에서 상호작용 가능한 오브젝트
3.  플레이어가 가진 물건
4.  최근 로그에서 언급된 대상
5.  인접 공간이나 알려진 장소
6.  전체 세계 단어장

이 우선순위는 세계가 확장된 뒤 조정한다.

중요한 제한:

-   후보는 플레이어가 볼 수 있거나 이미 알 수 있는 것에서 나온다.
-   아직 발견하지 못한 숨겨진 상호작용은 후보로 보여주지 않는다.
-   후보는 플레이어를 대신해 행동하지 않는다. 플레이어의 의도를 완성하거나 확인할 뿐이다.
-   LLM을 쓰더라도 초기 파서의 source of truth로 두지 않는다. 후보 정렬, 자연스러운 표면 문장 생성, 애매한 입력 보조 정도로 역할을 제한한다.

구현 여부, 구현 범위, 구체적인 자료구조는 별도 검토 후 결정한다.
